# 跨入口取消与迟到输出验证（2026-10-20）

基线 `11f8ba96`，Claude 实现，范围见 PLAN §8 同名条目。只新增测试，未发现缺陷，生产代码未修改。

## 主进程（`SpeechActions.test.mjs`）

用真实的 IPC → IntelligenceManager → LLMHelper 链路。4 个场景共用一个受控 mock：用 Promise 屏障控制"已开始""已输出第一段""放出 `LATE OLD`"三个时间点。第一次请求忽略取消信号，后面的请求返回 `NEW ANSWER`。

| 场景 | 结果 |
|---|---|
| 快捷动作还没输出 → Answer/Stop | 通过 |
| 快捷动作已输出一部分 → Answer/Stop → 放出 `LATE OLD` | 通过 |
| 快捷动作已输出一部分 → 文字提交 → 放出 `LATE OLD` | 通过 |
| 文字流已输出一部分 → 快捷动作 → 放出 `LATE OLD` | 通过 |

每个场景都断言了：

- 替换前旧任务还在运行，替换后已取消；
- 新请求 `terminalStatus` 为 `completed`；
- 放出迟到输出并等旧请求收尾后，历史和用量里都没有 `LATE OLD`；
- 被取消的请求没有记成 `completed`；
- 新回答在历史里只出现一次；
- 旧请求没有输出时，历史里不留旧回答；已输出一部分时，只保留已显示的那部分（现有的 `recordPartial` 设计）。

文字流场景还断言了：旧流没有发出迟到 token，也没有发出成功的 `gemini-stream-done`。

## preload（`ManualAnswerBridge.test.mjs`）

在测试里执行真实的 preload，传入假的 `ipcRenderer`，向它注入带旧请求 ID 的迟到 token 和终态。

- **快捷动作 → 文字流**：旧快捷动作的迟到 token 和终态都没有送达；新文字流的 token 和完成事件正常送达。
- **文字流 → 快捷动作**：切换时向主进程发送了 `gemini-chat-stream-stop`；旧流只收到切换时发出的那一次取消通知，迟到 token 和成功完成事件都没有送达；新快捷动作的 token 和终态正常送达。

## 边界

只能说"本次跨入口取消与迟到输出验证完成"，不关闭整个生成协调主题。

验证的是两层：主进程的任务、历史和用量，以及真实 preload 的事件过滤。不包括：

- `main.ts:1639-1652` 的事件转发层；
- 完整的界面端到端测试；
- 真实服务。

另外：

- 不做变异检查。`PreparedInputs.begin()` 本身就会中止旧任务，删掉某一处清理不一定让测试失败，这样的变异证明不了什么。
- 取消后不提供重试，这是现有策略（`preparedInput.ts:79`）。重试沿用现有测试。
- Windows 只做静态审查；不安装新版。

## 验收复查后的测试修正（2026-10-20）

复查发现上面的公开提交 `f49109f5` 里有两处验收证据缺口，都在测试里，不涉及生产代码：

- **旧流完成事件读错了位置**：`gemini-stream-done` 发送的参数是 `(clientStreamId, metadata)`，元数据在记录里排第 3 项，原断言却读的第 4 项，取到的始终是 `undefined`。这样即使旧流错误地发出了完成事件，断言也会通过。现已改为读第 3 项，并且只把 `status === 'completed'` 视为误报成功，取消状态的结束通知不算。
- **记录写宽了**：前文说"每个场景"都检查了新回答在历史里只出现一次，但第 4 个场景原先没有这条断言。现已补上。

改正后的断言做过一次反向确认：临时注入一条旧请求 `status: 'completed'` 的完成事件，测试失败，报出的正是"the old stream does not finish as a success"；恢复后文件哈希与改动前一致。

改正后，6 条交叉测试连续 3 次均为 6/6。本地完整门禁 16/16，全部 exit 0：单元测试 1213/1213，回答 21/21，存储 3/3，启动 2/2，挂载界面 14/14，来源检查 0 命中。改正后的测试尚未推送到公开仓库，也没有再跑公开 CI。
