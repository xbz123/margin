# Answer / Stop 口述与 What to answer 的问题来源（2026-11-10 至 11-12）

统一分支 `codex/margin-unified` 上的一组修改，起因是用户在 Windows 测试包上用豆包流式转写时，Answer / Stop 的问题里会叠加之前说过的话。用户要求参照旧 Margin 的做法（按下 Answer 不切断连接，按下前已经开口的半句自动纳入），并确认最关心的是把面试官一路的话作为问题。实现和测试由 Claude Opus 5.5 子代理完成，每轮都有独立的只读审查；主线程核对改动、提交、跑 CI、出测试包并做 Windows 真机复测。

## 现在的行为

### What to answer

- 单击即可。问题取面试官一路最近 4 段话（包括还没说完的那句），显示为问题气泡，再据此作答。
- 点击后的尾窗（最多约 3 秒）里，服务商如果把点击时已经识别出的文字从原片段挪到一个新片段，这部分文字仍然留在问题里。点击之后才开口的新一句不收。

### Answer / Stop

- 按下 Answer 只记录时刻，不动转写连接。
- 按下 Stop 时冻结这一轮：麦克风一路口述的文字就是问题；面试官一路的转写作为上下文交给模型。
- 麦克风一路哪些话算这一轮：
  - 按下之后才出现的；
  - 按下时还没定稿、之后又被修订或定稿的（按下前已经开口的半句因此整句纳入）；
  - 按下时还没定稿、且按下前 5 秒内更新过的。
- 不算这一轮：
  - 被更早一次动作结束的那次请求里的话，即使它的最后结果迟到；
  - 按下前已经空闲超过 5 秒、按下后只是被定稿或加了标点的句子（忽略标点、空白、大小写和数字写法后文字相同）。
- Stop 时麦克风一路没有口述、也没有附件：
  - 面试官一路在“按下 Answer 前 15 秒”到“Stop”之间说过话：不再提示未检测到语音，用这次 Stop 冻结的同一份内容按 What to answer 的方式作答，不重新收集、不多等；
  - 否则仍提示未检测到语音。
- 上一轮还在收尾时再按 Answer：上一轮照常出问题和回答，新一轮单独开始。之后再按 Stop 即开启新问题，上一轮被取代（还在收尾的不出气泡，正在输出的回答被截断）。用户 2026-11-12 确认这是预期行为。

### 豆包、阿里云的连接

- 每次手动动作（What to answer 等快捷动作和 Stop）冻结时，只对麦克风一路的豆包/阿里云请求发结束帧，等最后一包（最多 3 秒），之后的音频进入一个新的请求。面试官一路不结束请求，走限时尾窗。
- 豆包按请求内的句序号标识一句话，并对已发出的定稿做文本去重。

## Windows 真机复测（test.8，Windows 11 build 26200，真实豆包）

方法：把安装包解到单独目录运行，与安装版共用用户数据；通过调试端口操作界面，在主进程挂只读钩子记录转写事件；语音用合成语音直接写入对应一路的转写通道，注入期间丢弃该路的真实采集。

| 场景 | 结果 |
| --- | --- |
| 连续 4 轮口述，每轮只含本轮的话 | 通过 |
| 按下 Answer 前约 1 秒已开口，整句进入问题 | 通过 |
| 说一句后静音约 9 秒，按 Answer，不说话，Stop | 通过，提示未检测到语音 |
| Stop 后 0.7 秒再按 Answer，说一句，5 秒后 Stop | 通过，无错误提示，两轮各出问题 |
| Stop 后 0.7 秒再按 Answer，2 秒内再 Stop | 通过，上一轮被取代，无错误提示 |
| 面试官说到一半点 What to answer（3 次） | 通过，问题含正在说的那句 |
| 面试官说完后点 What to answer | 通过 |
| 文字提问、结束会议、退出 | 通过 |
| Stop 后继续把话说完，隔几秒再按 Answer 说新话 | 未通过：上一句的后半截出现在新问题开头 |

未通过那一项的原因：豆包对静音前的最后一句不定稿，下一次开口时把新话接在同一句上；口述归属按句判断，文字变了就整句收进。空闲旧话后面接着说新话是同一种情况。用户 2026-11-12 了解后未要求修改。

test.9 新增的行为只跑了自动化测试（本机相关套件 350/350），没有在真实应用里操作过。

## 真机测试中确认的豆包行为

- 一句话说完后如果是静音，一直停在未定稿，直到下一次开口或收到结束帧才定稿。
- 收到结束帧后 0.25–0.55 秒返回最后一包；新请求约 1 秒后可用。
- 新请求上的第一句偶尔返回空结果（14 次中 2 次），原因不明。
- 合成语音经扬声器外放再被麦克风收回的声音，豆包大多认不出（原生静音抑制把大部分样本置零）。这种方式不是有效的口述测试；test.7 一度因此被误判为口述失效。

## 没有验证的

- macOS 上的真机行为；用户计划在 Mac 上自行测试 test.9。共享逻辑在两个平台相同，平台差异只在声音采集。
- 真人对着 Windows 麦克风说话（真机测试绕过了真实麦克风采集）。
- 阿里云的真机行为。
- 审查记录的边界：按住 Answer 超过约 165 秒时面试官早先的话已不在收集范围；笔试模式下 Stop 的回退按面试方式作答；麦克风转写出错时如果面试官说过话，会直接作答而不显示麦克风的错误提示；服务商拆句时改写了新句开头的字，面试官正在说的那句仍可能丢失。
- 每次 Stop 后约 3 秒才出问题气泡，来自面试官一路的尾窗，未改。
